# 主角设定

## meta

```meta
name: 主角设定
id: protagonist
artifact: 设计.主角设定
declaration: >
  保存本局用户所扮演角色的身份名片，以及核心体验和已授权代演真正需要的最少信息。
when: |
  用户代入一个有独立身份、背景、关系或特殊能力的角色，且这些信息会影响核心体验或世界反应。
  LLM 获得较多推进权，而现有材料不足以稳定代演该角色时也使用。
when_not: |
  旁观、无固定主角或纯作者视角时不使用。刻意无名的自我投射不因缺名字而强制使用。
  NPC 有多份或需要统一字段时归生成规则，要留下的单条再写具体实例；世界硬法则归实现机制；第一幕归开场白。
boundary: |
  本能力只交用户角色名片和必要行为依据。体验与权限来自美学纲领，输入及推进方式来自故事推进，本步据此控制详略。
feeds: gm
```

## opening

```opening
说说这局里的“你”是谁。名字可以留作 `@玩家`；重点写会影响核心体验或世界反应的身份、背景、关系和特殊能力。只有需要 LLM 多代演时，才补性格与默认反应。
```

## task

```task
把用户材料整理为本局用户角色名片，写入 `设计.主角设定`。先保留承载核心体验的身份、能力、关系与限制，再按 LLM 获得的推进权决定是否需要行为依据。

用户自己扮演或提供详细大纲时，身份背景够用即可，不替用户设计人格与选择。LLM 代演越多，性格、处事倾向和默认反应越需要具体可执行。产物正文不放评分、追问或诊断。
```

## principles

```principles
1. 只设计用户已明确给出、核心体验依赖或运行确实需要的内容。
2. “首富之子”“唯我独法”等若是核心体验成立条件，属于必要设定，不算过度设计。
3. 特殊能力写“能做什么 + 限制”；世界为何如此由实现机制处理。
4. `称呼` 可写固定名字，也可写 `@玩家` 表示刻意留白；不要因无名阻塞成卡。
5. 行为依据随推进权增减：用户控制越多越简；LLM 代演越多越具体。
6. 不写 NPC 名片、世界百科、文风规则或开场事件。
```

硬规则：
1. 输出合法 JSON；`行为依据` 不需要时整项省略。
2. 不写产物内自评、追问、开放问题或完备度。
3. 不把核心体验所依赖的身份、能力或关系误删为“过度设计”。
4. 不替用户补未授权的人格、目标、情绪和关键决定。

## score

```score
宽松度：
- 5：只设计本局运行确实需要、核心体验依赖或用户已明确给出的部分；用户控制越多，留白越充分。
- 3：有少量未经确认、也非体验承重的性格或行为倾向，可能影响用户扮演但容易改写。
- 1：大量替用户设计人格、目标、情绪或行动逻辑，明显挤占用户控制权。

必要度：
- 5：核心体验所需的身份、能力、关系完整；代演信息量与 LLM 获得的推进权匹配。
- 3：缺一项会削弱核心体验或导致代演漂移的信息。
- 1：漏掉“我是谁、我凭什么获得该体验”的承重设定，或 LLM 需要代演却没有行为依据。
```

```checklist
- [ ] 称呼允许固定名字或 `@玩家` 留白？

```
