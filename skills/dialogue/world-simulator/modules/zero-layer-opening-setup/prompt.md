## opening

```opening
用持久卡的第一屏建立第一拍：玩家进场时在哪、哪些槽位一开始有内容、结束后显然能做什么。默认一条。还要别的入口时，每条再增殖一个开场节点；进游玩后左右切换，选中的一条作为 0 层。
```

## task

```task
读取程序已组装的 `设计.worker集`、`设计.0层回复呈现`、`设计.0层正文组成` 和其它最终层产物，写入 `设计.0层开场白与初态`。

默认生成 1 条。用户要多个入口时，每条再增殖一份产物，写入 `设计.0层开场白与初态#场景短码`；改某一条则覆盖同一完整 tag。不要把多条入口收成聊天里的选择题。每条候选必须携带一套不可混用的初态：
- 稳定候选 id 与一句区分。
- 可选用户角色名片。
- `zero-layer.card.v1` 初始卡：revision=0，包含所有可见槽位的初值或合同允许的空态。
- 与第一屏同真相的变量初值。
- 若有拓扑：当前位置、焦点和已揭示范围。

卡内模型生成槽位由本步填写；程序投影槽位只声明初始绑定，由程序从变量和拓扑初态灌入。正文槽的可见内容至少出现一次字面 `@玩家`。开场不依赖随机数，因此不输出任何 `名称.随机数` 的具体数组。

全部候选保存。游玩时左右切换，选中的一条作为 0 层：程序整套替换用户角色、卡状态、变量和拓扑初态，之后每轮只应用 `zero-layer.update.v1`，不新增可见助手楼层。

材料足够便直接成稿；会改变第一屏成立的缺口交给 `self_score.gap`。产物正文不放评分、诊断、追问或开放问题。
```

## principles

```principles
1. 第一屏、卡槽、变量和拓扑初态必须是同一个事实版本。
2. 默认一条。多条是不同入口，每条一个可增殖节点，各自一整套初态，不共享半套状态。
3. 所有可见槽位都必须有初值、允许的空态或程序投影绑定。
4. 只填模型生成槽；状态、地图和表盘从权威初态投影。
5. 用户角色没有名片时仍使用 `@玩家`；有名片时也不把姓名硬写进占位位置。
6. 不写 HTML/CSS/JS，不复制固定外壳，不在开场里模拟后续 slot_updates。
7. 本步结束后创作收口；后续变化进入持久卡更新协议。
```

## probe

```probe
每轮 1～2 点。优先确认第一拍、初始活动视图、模型槽初值、某项权威状态的开场值，以及多入口时整套初态差异。
```

硬规则：
1. 输出合法 JSON；候选默认 1 条，仅用户明确要求时 2～3 条。
2. `默认候选id` 必须指向候选之一；每条都是完整独立初态。
3. 初始卡 schema 固定为 `zero-layer.card.v1`，revision 固定为 0。

8. 产物正文不含自评、追问或开放问题。
9. `mount` 固定为 `["world-simulator", "narrator"]`。

## score

```score
第一屏可玩：
- 5：第一拍、当前信息和行动空间清楚，短到愿意立即开玩。
- 3：可以开玩，但当前目标或下一步略含糊。
- 1：像长篇序章，或看不出玩家能做什么。

卡合同符合：
- 5：全部可见槽位都有正确初值、空态或程序投影绑定，模式与0层合同一致。
- 3：主体符合，一个辅助槽位初值含糊。
- 1：漏槽、模式冲突或直接复制整页 HTML。

状态自洽：
- 5：第一屏、变量、拓扑和程序投影引用完全同真相。
- 3：主体一致，但一项次要初态依据不足。
- 1：叙述与初态冲突或程序槽由模型编造。

持久起点：
- 5：card_id 稳定、revision=0、初始视图明确，后续可直接应用 slot_updates。
- 3：可初始化，但初始视图或某槽持久语义略含糊。
- 1：仍按普通消息设计，无法形成持久卡。

候选切换：
- 5：默认明确；多条时每条入口与整套初态差异成立。
- 3：可切换，但多条差异偏弱。
- 1：候选共享冲突状态，或未要求却堆重复入口。
```

