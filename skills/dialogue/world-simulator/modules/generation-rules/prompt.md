# 生成规则

> 技能文档。程序只切割下方 **fence 块**；`##` 标题仅供人读。  
> 产物外壳：`docs/context-fragment-design.md`；范例：`aesthetics-interaction` / `mechanism`。  
> 正文高度自定义（描写文案、schema 字段、池随对象族而变）；外壳与规则键必须严。

## meta

```meta
name: 生成规则
id: generation-rules
artifact: 设计.生成规则
declaration: >
  要精准格式，或本局原创听了会雾且故事里还要生成时：写出该对象族怎么生成（描写/格式/可选池）；
  创意字段用方向池给创作范围，不堆枚举词；不填最终实例；可按对象反复
when: |
  已有「美学纲领与交互范式」或等价整体感觉，且下面两条满足一条就排（可按对象族反复）：
  a. 生成物必须有精准格式。例：武功典籍要有名字、效果、阶层。
  b. 本局原创、听了会一头雾水的东西，故事里还要随机/反复生成。例：人人能绽放的「心之彩」；当成本局原创的斩魄刀。
when_not: |
  整体感觉未钉 → 先「美学纲领与交互范式」。
  常识能推、也不需要精准格式（现实名车、西幻常见种族）→ 不排。
  只要几张具名名片、不必按规则生成 → 不排；已有规则再要名片 → 「具体实例」。
  跨轮记住什么 → 「变量设计与更新规则」。故事怎么往前写 → 「叙事指南与故事推进」。
boundary: |
  本技能：一条规则＝怎么描写/生成 + 单层 JSON 产物格式 + 可选池（方向池优先；元素池仅封闭集合）。
  具体实例：按规则填最终 records；本步不写最终实例（池≠实例）。
  舞台骨架 / 实现机制：可引用，不重写百科、不重钉既成法则。
  变量*：游玩期状态更新——本步只约束生成时的类型与合法初值范围。
  随机范围整理：把本步（及其他上游）里需要的掷骰/检定范围收成插入表——本步可写合法区间，不代替那份汇总。
  旁观维护：可读合同（rule_id、产物格式、何时可 need_generate）；程序抽样只抽元素池；方向池由填写方按规则自创。
feeds: gm,auditor
```

## opening

```opening
先认定本轮规则写哪一类内容：
- 若【本步对象】/【原型建议】已有对象提示，以此为起点；要改对象就在本步改。
- 若规划为空，先钉对象族，再谈规则。

然后谈：
1. 生成出来必须钉死哪些字段吗？（如武功典籍的名字、效果、阶层）没有就说没有。
2. 这是不是本局原创、听了会一头雾水、还要在故事里随机生成的东西？
3. 更需要：开局先钉一批、游玩中再随机补，还是只在游玩期动态生成？
4. 这类实例彼此有没有必须同场钉死的关系（如互为亲属、对立、同场搭档）？有 → 一次同批生成；彼此独立 → 一次一条。
5. 有没有必须全员一致、能数完的标签（阶层、强度档、武器种类）？名字、能力、气质、外貌这类写不完的，后面用「方向」划范围（一句话概括即可，少举例）。阶层这类光看名字不懂的，后面会写成能看见/听见的对照，不要只留阶名。

想到什么写什么；完整规则在正式产物里钉。
```

## task

```task
你正在执行「生成规则」。产物必须是 **context-fragment.v1** JSON，写入「设计.生成规则」。

本步写出的最终物是**规则**，不是实例。规则是创造这类东西的方法：空白表格 + 怎么填厚 + 必要时给方向。一条规则必须说清两件事，并可附第三件：
1. **生成与描写**：按什么顺序写、多方向如何拼进一格、每格填到多厚、分级如何被感知。
2. **产物格式**：生成结果必须遵循的可校验格式（schema）。描写字段要有粒度和地板。
3. **池**（可选，默认无）：优先 **方向池**（方向名 + 一句概括；默认不举例，至多点 1 个专名）；**元素池**只给能数完、必须全员一致的封闭集合。无则 `池: []`。

本步是〔先验产物〕：先定本轮对象族，再写规则。读【本步对象】与【原型建议】；在本步钉「写什么」。禁止顺手扩到其它族。

执行顺序：
1. 认定对象族：规划有 `target` 则采用（用户要改则以最新为准）；规划为空则先钉对象。不要停下来让编排器补参。
2. 对照时机 a/b：必须有精准格式，或本局原创听了会雾且故事里还要生成。两条都不成立 → 结论「无需专门规则」，`rules: []`。
3. 两项成立时，生命周期三选一（规划里 `lifecycle_intent` 合理则采用）：
   - `runtime_only`：仅游玩期动态生成；不要求「具体实例」。
   - `seed_only`：由「具体实例」预生成；规则用完可丢。
   - `seed_and_runtime`：先种子实例；规则与实例都保留，游玩期仍可按同规则生成。
4. 钉「数量」与「一次生成」（两件不同的事）：
   - **数量**：这类对象总共要有几条（fixed / range / contextual）。
   - **一次生成**：点一次「具体实例」交几条。彼此有必须同场对齐的关系 → `同批`；彼此独立 → `单条`。产物形状始终是 `records[]`。
5. 写字段前先做设计判断（写入该 rule 的 `设计判断`）：
   - 列出 **不可穷举项**（姓名、绰号、能力概念、外貌手感等理论上写不完的）→ 这些用方向池或自由写，禁止做成条目枚举。
   - 列出 **封闭集合**（阶层、强度档、有限类型名）→ 这些才用 `allowed_values` 或一个元素池。
   - 标签本身看不懂的分级（境界、品阶、强度档、好感档等）→ 必须另写 `分级表现`，把每档写成可感知的详细表象，不要只留字母/阶名。
   - 从本对象族真正用得上的面挑 3～6 个正交字段（是什么 / 能做什么 / 和谁关联 / 怎么被感知），不要摊通用名片。
   - 外貌、服装、仪式等由几面拼成一格的 → 写 `配方`（多方向组装进同一个顶层字段），不要拆成嵌套对象，也不要为每一面各建元素池。
6. 写满规则：生成与描写（含配方、表现、工作流、反模式）+ 产物格式（**单层 JSON**）+ 池（需要才填）+ 需要时的分级表现。
   每个描写类 string 字段必须有 `粒度`（句子）和 `地板`（填到什么才算够）。`示例形状` 必须达到地板，禁止用单标签当示例。
7. 逐字段过筛：每个属性都要能回答「对本对象族是否必要」。冗余字段删掉（如女主规则里的「性别」）；玩法接口不得漏（如 D&D 怪物的等级、攻击骰）。
8. `rule_id`：规划已给则用；否则稳定 kebab-case。已有产物按 rule_id 增量。
   若本步对象与规划不一致，以最新对象为准并重钉对应英文 rule_id，禁止沿用旧 id。
9. 按自评四维打分并填追问；输出 JSON。禁止夹带最终实例 records。

若程序已发默认问题：禁止重复开场；在首答上补洞。
summary：建立 → `生成规则 · {对象} · {仅动态|仅预生成|预生成并动态} · {单条|同批}`；跳过 → `生成规则 · {对象} · 无需专门规则`。
```

## principles

```principles
1. 整条规则先问必要性：时机 a（精准格式）或时机 b（原创会雾且还要生成）是否成立？两条都不成立则跳过，勿硬造表。
2. 一调用一对象族；格式或用途不同则分次编排。
3. 规则 = 描写/生成方法 + 产物格式。池不是必填第三设计；默认 `池: []`。宁少池，勿为每个字段挂一套词表。
4. 属性逐个过筛：每个字段必须对本对象族有意义；禁塞通用名片字段，也禁漏掉玩法接口字段。
5. 产物格式 = **单层 JSON**：一条产物是一层扁平对象；值仅为标量或「标量数组」。
   禁止嵌套 object、禁止 object 数组。此格式要对齐动态表格列、旁观者→主世界层生成、以及投影取字段。
   类型/必填/枚举/上下界必须可校验；禁止只给示例让下游猜类型。
6. 池分两种，先判断能不能数完：
   - **方向池**（默认）：选项理论上无限。给 4～8 个方向；每条以**方向名 + 一句概括**为主。默认不举例；需要手感时至多点 1 个专名，禁止把方向写成作品名/例句清单。填写以方向为主：方向名可以当选项或标签；句子级字段按该方向写开。程序不抽方向池。
   - **元素池**：选项有限且必须全员一致（阶层、武器种类、强度档字母）。条目可穷举；旁观 `need_generate` 只抽这类池。
   姓名、绰号、能力概念、外貌、气质（作描写时）禁止元素池，也禁止用 `allowed_values` 假穷举。同一封闭集合不要既写枚举又再建元素池。
7. 填值要有地板。骰子、是否可破坏可以短。外貌、能力现象、限制、互动手感必须写到可感知。`示例形状` 是地板的样板，不是「阴郁」这种标签。
   分级标签本身看不懂时：实例字段仍填短档位；详细对照写在 `分级表现`（每档 = 一句概括 + 一段可感知表象，相邻档必须能分清）。不要只丢「A / 金丹」让人猜。
8. 几面拼成一格用 **配方**：点名目标字段、用到哪些方向组件、怎么拼进这一格。表现类要点用 **表现**：一句概括 + 至多 1 条例子；例子是密度样板，不是选项库。
9. 生命周期先行；未定前不假装可执行「具体实例」。
10. **一次生成**看关系，不看「想不想一次多写」：有必须同场钉死的关系 → `同批`；彼此独立 → `单条`。`同批` 至少 2 条。不要把「总共要几个」和「这一次交几条」混成一件事。
11. 不写变量更新公式、不写剧情推进、不填最终实例。
```

## probe

```probe
每轮 1～2 点。规划已钉且用户未改对象时，禁止重问 target / rule_id。规划为空或用户要换对象时，先问本轮生成什么。

优先：整条规则是否必要；实例彼此有无必须同场对齐的关系；某字段该不该进表；不可穷举项有没有被错做成枚举词表；分级标签够不够让人看懂；描写字段地板是否够用。
若时机 a/b 都不成立 → 建议跳过，停追问字段与格式。
不追问：最终实例正文、变量增减公式、其它对象族、完整世界百科、再给哪个字段加一套枚举池。
```

```output
      }
    ]
  },
  "开放问题": []
}
```

硬规则（公共三段 + 本技正文）：
1. 合法 JSON；必含 `schema` / `技能` / `brief` / `正文` / `自评` / `追问`（题目可 `[]`）。
2. **公共三段**：正文＝规则主体；自评＝必要性/属性妥当/材料得当/格式准确（**分数 0–10 十分制**）；追问＝导语+建议选项。
3. **正文键固定**：本步参数、必要性判断、rules、增量说明。
4. **每条 rule 必含**：设计判断、生成与描写、产物格式、数量、一次生成；**池可空数组**。`生成与描写.配方` / `表现` 无则 `[]`。标签看不懂的分级必须有 `分级表现`（每档概括+表象，相邻可分清）；无此类则 `分级表现: []`。有池时 `绑定字段` 必须是单层 schema 的顶层键，且必须标 `池型`。多个方向池绑同一字段时配方必须写清怎么拼进该格。`一次生成.模式` 为同批时 `关系` 必填且本批至少 2 条；为单条时一次只交 1 条。
5. **产物格式强制单层**：`schema` 的 `type` 不得为 `object`；`array` 的 `items` 不得为 object。禁止 `外貌.发色` 这类嵌套路径。描写类 string 字段必须有 `粒度` 与 `地板`；`示例形状` 必须达到地板。
6. **池型**：`方向` 必须有 `方向`（对象：方向名→一句概括，4～8 条；默认不举例，至多 1 个专名），`条目` 可 `[]` 或省略。`元素` 必须有可穷举 `条目`，不要写 `方向`。不可穷举项禁止 `池型=元素`，也禁止用 `allowed_values` 冒充。
7. 结论为「无需专门规则」时：`rules` 必须 `[]`。上下文策略布尔须与生命周期一致。
8. 池≠最终实例；禁止输出具体实例 `records`、变量更新规则、执行单元列表。
9. `mount` 默认主世界层 + 旁观维护（旁观只需合同键：rule_id/格式/必要性；描写长文可在投影时 summary）；**禁止**写 `order`。summary 见 task。

## checklist

```checklist
- [ ] 含 schema / brief / 正文 / 自评 / 追问？
- [ ] 自评为必要性 / 属性妥当 / 材料得当 / 格式准确？
- [ ] 整条规则必要性有举证？不成立时 rules=[]？
- [ ] 建立时：有设计判断（不可穷举 vs 封闭集合）？逐字段无冗余无漏接口？产物为单层 JSON？数量与一次生成已分清？
- [ ] 描写字段有粒度+地板，示例形状不是单标签？
- [ ] 该细的分级有概括+可感知表象，不是只留阶名？
- [ ] 多方向拼一格时有配方？表现是概括+极少例子？
- [ ] 池：无则 []；有则标池型；方向池以概括为主、例子极少；元素池仅封闭集合；未把名字/能力做成枚举词表？
- [ ] 未夹带最终实例、变量公式、其它对象族、百科？
```

## examples

```examples
好：
- 武功典籍：单层含 名字/效果/阶层。阶层短填 + `分级表现` 把每阶写成可感知对照；名字与效果用方向池（方向名+一句概括）。
- 外貌：轮廓方向 × 质感方向，配方拼进 `外貌` 一格，不要 `{发色:{}}`。
- 「心之彩」：颜色/性格用方向池（如「冷焰：静、刺、余烬不散」），不要列出 20 种色号，也不要堆作品名。
- D&D 怪物：名称/等级/攻击骰齐全；等级若只写数字看不懂，补分级表现；气质用方向池+句子地板。
- 女主规则：不设「性别」；池可空；内在冲突自由写并给地板。
- 互为仇敌的两名开局 NPC：一次生成=同批；可互换的酒馆路人：一次生成=单条。
- 现实名车、西幻常见种族 → 无需专门规则。

坏：
- 为气质/花招/绰号/能力各建一个 8～20 词的元素池，填出来全是标签。
- 方向池每条挂 3 个作品名或例句，变成假选项库。
- 产物写成 `{ "外貌": { "发色": "…" } }` → 非单层。
- `示例形状` 里 `能力描述: "时空斩"` 或 `气质: "阴郁"` —— 地板被示例教坏。
- 阶层/强度只有「A」「金丹」，没有表象，叙事时没法写。
- 女主规则塞「性别」；或怪物规则只有「名字+性格」没有等级/攻击骰。
- 有亲属关系的三人却标成单条；或把「总共要 5 个」写成同批但彼此无必须同场的关系。
- 把写好的 NPC 整份塞进池当最终实例。
```
